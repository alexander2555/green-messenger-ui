# Спецификация: чат-интерфейс для MAX (GREEN-API)

Черновик для дальнейшей разработки. Основан на приложенном ТЗ (TS_GREEN-API_MAX.md) и официальной документации GREEN-API (green-api.com/v3/docs).

## 0. Принятые решения

- В форму входа добавляется поле **apiUrl** — итого 3 поля: `apiUrl`, `idInstance`, `apiTokenInstance`.
- Настройку приёма уведомлений (`webhookUrl` пуст, `incomingWebhook = yes`) пользователь выполняет **сам, один раз, в личном кабинете GREEN-API**.
- Архитектура сразу закладывает **адаптер под разные мессенджеры** (не только MAX) — см. раздел 3a. Реализуется в этой итерации только провайдер для MAX, но интерфейс и хранение credentials рассчитаны на несколько провайдеров.

## 3a. Адаптер под мессенджеры (провайдеры)

GREEN-API уже сам по себе достаточно единообразен между мессенджерами: методы для WhatsApp, Telegram и MAX вызываются по одному и тому же шаблону адреса (`{apiUrl}/waInstance{idInstance}/{method}/{apiTokenInstance}`).
Поэтому адаптер в первую очередь абстрагирует не разный синтаксис запросов, а разные **наборы правил и учётных данных**: у каждого мессенджера — свой отдельный инстанс GREEN-API (свои `apiUrl`/`idInstance`/`apiTokenInstance`), свои ограничения формата номера телефона (для MAX — только RU/BY) и, потенциально, свой набор полей ответа.

Интерфейс провайдера (значения — иллюстрация состава):

```ts
interface MessengerProvider {
  readonly id: 'max' | 'whatsapp' | 'telegram';
  sendMessage(chatId: string, text: string): Promise<{ messageId: string }>;
  checkAccount(phoneNumber: string): Promise<{ exists: boolean; chatId: string }>;
  pollNotifications(onIncomingText: (chatId: string, text: string) => void): () => void; // возвращает функцию остановки
}
```

`ConnectionsContext` хранит **список** подключений (по одному на мессенджер, к которому пользователь подключился), а не одну тройку значений. Экран настроек позволяет добавить подключение, выбрав тип мессенджера и введя его собственные `apiUrl`/`idInstance`/`apiTokenInstance`. В этой итерации реализуется только `MaxProvider` по контракту из раздела 4.

## 4. Контракт GREEN-API для MAX (по официальной документации)

Базовый шаблон адреса метода:

```
{apiUrl}/waInstance{idInstance}/{method}/{apiTokenInstance}
```

`apiUrl` — **индивидуальный для инстанса** хост вида `https://3100.api.green-api.com`. Заголовок `Content-Type: application/json` для запросов с телом.

| Метод | HTTP | Путь | Тело / параметры | Ответ |
| --- | --- | --- | --- | --- |
| SendMessage | POST | `/sendMessage/` | `{ chatId, message, typingTime?, quotedMessageId? }`. `message` — до 4000 символов, UTF-8 без BOM | `{ idMessage }` |
| CheckAccount | POST | `/checkAccount/` | `{ phoneNumber: <11-12 цифр, только RU (7) и BY (375)>, force? }` | `{ exist, chatId, fromCache }` |
| ReceiveNotification | GET | `/receiveNotification/?receiveTimeout={5-60}` | — | `{ receiptId, body }` либо пустой ответ по таймауту (long-polling, по умолчанию 5 сек) |
| DeleteNotification | DELETE | `/deleteNotification/{receiptId}` | — | `{ result: boolean, reason }` |

Лимиты частоты запросов на инстанс (превышение → HTTP 429): SendMessage — 50/с, CheckAccount — 10/с, ReceiveNotification и DeleteNotification — по 100/с. Для нашего сценария (один пользователь, один поллинг-цикл на подключение) лимиты не критичны.

**Идентификатор чата (`chatId`)**: рекомендованный поток — получить `chatId` через `CheckAccount(phoneNumber)`, затем использовать именно его в `SendMessage`. Устаревший формат `{phone}@c.us` тоже поддерживается для отправки, но сервер всё равно назначит "канонический" `chatId`, который придёт во входящих уведомлениях — то есть при отправке по номеру сверка "исходящий чат = входящие ответы" усложняется. Поэтому для сопоставления исходящих и входящих сообщений в одном чате нужно всегда работать с `chatId` из `CheckAccount`, а не с `{phone}@c.us`.

## 5. Получение сообщений (long polling)

ТЗ требует технологию HTTP API (не Webhook Endpoint), то есть цикл на каждое активное подключение:

1. Предусловие (выполняется пользователем заранее, вне приложения): инстанс настроен на приём через HTTP API — `webhookUrl` пуст, включены нужные типы уведомлений.
2. В фоне (пока открыта вкладка) — цикл: `GET receiveNotification` (ждёт до N секунд) → если пришло уведомление типа `incomingMessageReceived` с `messageData.typeMessage = "textMessage"` — добавить в список сообщений этого `chatId` → `DELETE deleteNotification/{receiptId}` → повторить.
3. Уведомления, не относящиеся к текстовым входящим сообщениям (статусы, сервисные), — подтверждать (`DeleteNotification`), но не отображать в UI.

**Важное ограничение**: получение сообщений работает только пока вкладка браузера открыта и выполняется JS-цикл. GREEN-API хранит недоставленные уведомления в очереди до 24 часов, поэтому сообщения не теряются — но появятся в интерфейсе только при следующем запуске приложения, а не в реальном времени, если вкладка была закрыта.

Это прямое следствие отказа от бэкенда (раздел 1).

## 6. Хранение учётных данных

Список подключений (каждое — `{ provider, apiUrl, idInstance, apiTokenInstance }`) сохраняется в браузере (localStorage), чтобы не требовать повторного ввода при каждом заходе (пользователь вводит свои учётные данные один раз при первом переходе на сайт).

Компромисс: **риск при XSS** -> **не хранить никаких дополнительных персональных данных**
